# Plan a Layer Change

`{{command_name}}` in layer `{{name}}`: turn a request to change how agents work into the smallest change to an agentic layer that satisfies it, written as a plan another agent can execute without asking a single question. Plan only; change nothing.

## Variables

REQUEST: $1
PLAN_FILE: ${specs_dir}/layer-change-${adw_id}-<descriptive-name>.md

## What you are changing

{{codebase_description}}

An agentic layer is the set of prompts, workflows and rules around a codebase. It has exactly two kinds of source, and only these may change:

- the definition `agentic.rkt`, a `#lang al` program; `AL-DSL.llms.txt` next to it is the complete language (anything it does not list does not exist);
- layer-local templates under `templates/commands/`, `templates/hops/` and `templates/experts/`, each replacing the kit template of the same name for every command, hop or expert that uses it.

Everything else in the layer is generated by `al gen` and overwritten by it: `commands/`, `hops/`, `experts/*/*.md`, `adws/`, `env/`, `fabric/`, `forge/`, `agentic-layer.json`, `README.md`, `AL-DSL.llms.txt`, `.gitignore`, `.al-manifest.json`. Never plan an edit to a generated file: `al gen` refuses to overwrite a hand edit, so such a plan fails its checks.

## Instructions

- You are in `${worktree}`, a git worktree of the repository that holds the layer. Read it, do not modify it. The only file you create is PLAN_FILE. Never switch branches, push, or touch the main checkout.
- Read, in this order: the layer's `AL-DSL.llms.txt` in full, its `agentic.rkt` in full, its `LLM.txt` (what the codebase is), every file under its `templates/`, and the generated prompts under `commands/` and `hops/` that REQUEST is about, so you know what agents are told today.
- Think hard about what REQUEST really asks for, and choose the smallest change that satisfies it. Prefer, in this order, and say in the plan which you chose and why the earlier ones do not fit:
  1. a change in `agentic.rkt` using the language (a new or changed option, field, command, step or workflow);
  2. a `#:focus` line on an existing command in `agentic.rkt` (a short, permanent instruction for that one prompt);
  3. a layer-local template: eject the kit template with the `eject` command below, then edit the copy under `templates/`; keep every `{{…}}` placeholder of the kit template exactly as it is and add no new ones (an unknown placeholder is an error at `al gen`);
  4. a new custom template (`#:template custom #:file "templates/…"`) registered in `agentic.rkt`.
- A change to a template changes every command that uses it. Name those commands.
- Change only what REQUEST needs. Never loosen a check, a review or a protected path, and never remove a workflow, unless REQUEST explicitly asks for exactly that.
- Use only names that `agentic.rkt` declares, or declare them in the same change. Every new name must follow the rules in `AL-DSL.llms.txt`.
- State, for a person who does not read Racket, what will be different for them after the change is merged: what they can now do, what agents will do differently, and anything they must do themselves. Write it under `## What changes for you`.
- If something cannot be done inside the layer (a secret, a new tool on the machine, a change to the application itself), plan the rest and add a line starting `REQUIRES HUMAN` under What is left out.
- A plan covers building and validating only: no step commits, merges, pushes, tags, releases or opens a pull request; delivery is the workflow's. Integration work (bringing in another branch or patch) is planned as 'apply onto the worktree, uncommitted', e.g. `git merge --no-commit --squash <ref>`, `git checkout <ref> -- <path>` or `git apply`.
- Write PLAN_FILE in exactly the Plan Format: keep every heading, replace every `<placeholder>`, add no sections. `<descriptive-name>` is 3-6 lowercase hyphenated words.

## Plan Format

```md
# Layer change: <name>

## Request
<REQUEST, verbatim>

## Summary
<two or three sentences: what changes in the layer and why this is the smallest change that satisfies the request>

## What changes for you
<bullets in plain language for someone who does not read Racket: what they can now do, what agents will do differently, what they must do themselves after merging (for example where to write tasks)>

## How
<the mechanism chosen (definition change, focus line, layer-local template or custom template), why, and which commands, hops or workflows it affects>

## The change, step by step
```
